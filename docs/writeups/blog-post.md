# Ranking climbers nobody else will

The first time I cared about IFSC rankings, I noticed something strange: an athlete who'd just won a World Cup final could *lose* rank points to someone who placed eighth at three smaller events. The official system rewards attendance. It doesn't really care who you beat, or how. For a sport where the gap between "wins gold at Olympics" and "barely qualifies for finals" is sometimes a single failed move on a single problem, that felt wrong.

So I built my own.

[Climbing ELO](https://climb-elo.vercel.app) is a rating system for World Cup–level competition climbing — Lead, Boulder, Speed, and the Olympic Boulder+Lead combined format. It scrapes results from the official IFSC results API, computes Glicko-2-flavoured ratings that weight opponent uncertainty, and serves a dashboard with leaderboards, athlete profiles, head-to-head probabilities, and Monte Carlo projections for upcoming events. It's small, single-author, and entirely open. This is a write-up of the engineering decisions that shaped it — what I'd say to someone considering building something similar.

## The math, in one paragraph

The core is Plackett-Luce: any multi-athlete finishing order can be decomposed into all pairwise contests, and each pair updates symmetrically (zero-sum on μ). The per-pair K-factor is normalised by field size — without that, a 30-athlete World Cup final would swing ratings 15× more than a 2-athlete event. On top of that, Glicko-2's rating-deviation φ modulates everything: an established athlete beating a cold-start athlete (high φ) earns *less* than they would for beating a peer, because we don't yet trust the comparison. φ inflates during inactivity via Glicko-2's Wiener-process formula (`φ_new² = φ_old² + σ² · months_inactive`), so a comeback from a multi-year sabbatical produces appropriately uncertain ratings. Margin-of-victory rides on top via a multiplier that's *damped when the favourite wins* — 538's NFL/NBA experience showed that letting elites bank the full MOV bonus inflates the top of the distribution; we keep the bonus for upsets and shrink it asymmetrically when the rating gap predicted the outcome anyway. The whole composition is `K_eff = K_base(tier, round) × g(φ_opponent) × margin_mult(rating_gap)`. Five small ideas, layered. Each by itself is one improvement; together they're a rating that responds to the *shape* of a result, not just its rank.

## What I learned by deploying it

The hardest parts weren't the math. They were the production realities that no document warns you about.

**Three connection strings for one database.** Supabase exposes three different URLs for the same Postgres project. The direct one (`db.PROJECT.supabase.co:5432`) is IPv6-only — and GitHub Actions runners don't have IPv6. The transaction pooler (port 6543) is what serverless functions need, but it rejects any statement that depends on session state (advisory locks, prepared statements outside a single statement). The session pooler (port 5432, IPv4) is what bulk-insert workflows need, but it isn't right for short-lived serverless invocations. I learned this by watching the same SQLAlchemy code work locally, time out in CI, and 500 in production — three failures, three different fixes. The lesson stuck: "Postgres is Postgres" is the *application* abstraction; the *operational* abstraction is "three connection strings, picked per compute environment." I now document this kind of thing in the project's engineering reference the moment I figure it out.

**Vercel's Python runtime statically introspects your entry point.** I had wrapped `create_app()` in a try/except so I'd see real tracebacks instead of opaque `FUNCTION_INVOCATION_FAILED` pages. The wrap broke deployment entirely — Vercel's static analyzer parses the entry-point module looking for a top-level `app = ...` assignment, and burying it in a try block hides it. The fix was two assignments: one outside the try (satisfies the analyzer), one inside (the one that actually runs). Frameworks promise "deploy any FastAPI app." They don't tell you that statically-introspected platforms constrain how you *express* the app.

**Sometimes the right fix is to delete the thing.** Mid-project I hit a bug where a fitter script couldn't produce real numbers because my local SQLite was on a pre-migration schema. My first instinct was to file an issue: "Add a schema-refresh script for local SQLite." I caught myself before implementing it. The local SQLite existed only because the code had a "fallback to local SQLite if `DATABASE_URL` isn't set" path — a convenience that made sense when I added it, but had become actively harmful (silently running against a stale schema instead of failing loudly). I deleted the fallback entirely, removed 743 lines of supporting code, and replaced it with a single `RuntimeError`. The project got simpler, not poorer. I now ask "should this thing exist?" before "how do I fix this thing?" — the second question hides the first.

## Orchestrating yourself across a long day

A lot of this project was built with parallel background agents. That sounds glamorous; the reality is more like managing a small team where every member writes code an hour faster than you can review it. The two patterns that turned out to matter most:

**Plan before you build.** For changes that touch foundational math — the Glicko-2 integration, the field-strength + activity classifier — I dispatched a *planning* agent first whose only deliverable was a written document. The Glicko-2 plan came back at 488 lines: file:line references for every integration point, the exact formulas from Glickman 2013 that would replace the existing math, three open design decisions flagged for me to answer. When I then dispatched the *implementation* agent, I baked those three answers into its prompt as locked-in. The agent didn't re-litigate; it executed. The result shipped in a single commit, full test suite passing, including a cold-start trajectory test using real athlete IDs. Plan docs are cheaper than implementation re-runs. The cost of producing a 500-line markdown doc up front is a small fraction of the cost of redoing implementation work because two parallel agents answered the same architectural question differently.

**Parallelism is gated by merge graphs, not by intelligence.** Four agents in parallel works when their file sets are disjoint. Two agents both touching `engine/elo.py` is asking for a non-fast-forward push and a manual rebase. I learned to draw the dependency graph before dispatching: `R1 (Glicko-2) → R3 (MOV gap-conditioning) → EloConfig refactor → K-regrid sweep`, with `R4 (Boulder+Lead weights)`, the local-SQLite cleanup, and the rich-profile work all branching off in parallel. The constraint isn't whether the agent can do the task. It's whether the agent's commits will collide with everyone else's at merge time.

## What it looks like now

Production lives at https://climb-elo.vercel.app. The dashboard has a leaderboard with three view modes (default is "active in last 12 months" — Glicko-2's σ inflates during inactivity but μ doesn't decay, so without this filter you'd see athletes who haven't competed in five years sitting in the top-50). Click through to an athlete profile and you get a Chart.js rating-over-time graph, a photo and body metrics where IFSC publishes them, and their last 20 events with pre/post μ deltas. The breakdown page for any (athlete, event) pair shows every pairwise contest contributing to the rating change. The Monte Carlo projector takes the registered roster for an upcoming event and simulates the bracket 10,000 times.

Under the hood: FastAPI + SQLAlchemy + Jinja2 on Vercel's Python runtime, backed by Supabase Postgres. uv for dependencies. ruff + pytest in CI, gated on Python 3.11 and 3.12. A nightly GitHub Actions workflow scrapes upcoming events and recent results, runs the ELO backfill for all three disciplines, refreshes the combined Boulder+Lead aggregate, and enriches athlete profile data. The whole pipeline is idempotent — re-runs are safe and produce no duplicates.

The current open backlog is mostly research: a Whole-History Rating batch refit alongside the online ELO, a bracket-native Speed model that replaces Plackett-Luce on time-normalised results with actual head-to-head matchups + Davidson tie-handling, a G-Elo benchmark comparison. The shipped Glicko-2 + MOV + tournament-participation-bonus combination beats the IFSC official ranking by +37.5pp on Lead and +77.8pp on Boulder in the backtest — a margin I expect WHR to narrow rather than widen, because the marginal improvements get harder.

## The thing I'd say to someone building something like this

The work *is* the iteration. The codebase that exists at the end of a focused day isn't the codebase that existed at the start, and it isn't final either. The next iteration is already queued. Production knowledge is paid for in outages — there's no document you can read up front that will save you from learning the three Supabase connection strings the way I did. Plan documents are cheaper than implementation re-runs. Parallel agents work only if you've thought about the merge graph before dispatching. And the right fix is sometimes to delete the thing causing the problem, not to maintain it harder.
